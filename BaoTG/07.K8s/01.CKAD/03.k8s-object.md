# TÌM HIỂU VỀ KUBERNETES OBJECT
## Bản chất của Kubernetes Object
- Thực thể bền vững (Persistent Entities): Kubernetes sử dụng các object này để ghi lại trạng thái toàn bộ cụm của bạn. Khi bạn tạo một object thành công, hệ thống sẽ lưu nó vào kho lưu trữ trạng thái (etcd).
- Mô tả "What" thay vì "How": Một Kubernetes Object đại diện cho một "record of intent" (bản ghi ý định). Khi bạn tạo object, bạn đang nói cho Kubernetes biết: Tôi muốn hệ thống ở trạng thái như thế này. Sau đó, các tiến trình ngầm của K8s (Controllers) sẽ tự động làm mọi cách để biến thế giới thực tế khớp với ý định đó.

## Cấu trúc trường dữ liệu bắt buộc (Object Spec)
Bất kỳ file cấu hình YAML/JSON nào mô tả một K8s Object đều phải chứa các trường cấp cao (top-level fields) sau:
- apiVersion: Phiên bản Kubernetes API bạn đang dùng để tạo object này (ví dụ: v1, apps/v1).
- kind: Loại đối tượng bạn muốn tạo (ví dụ: Pod, Deployment, Service).  
- metadata: Dữ liệu giúp định danh duy nhất đối tượng, bao gồm:
    + name: Tên của object.
    + namespace: Không gian tên phân tách môi trường (mặc định là default).
    + uid: Mã định danh toàn cục (UUID) do K8s tự sinh ra.
    + labels và annotations: Các nhãn dán định danh hoặc chú thích bổ sung.
- spec: Trạng thái mong muốn (Desired State) do bạn tự thiết kế và cung cấp. Bạn mô tả cấu hình chi tiết ở đây.
- status: Trạng thái thực tế (Actual State) do Kubernetes tự động cập nhật và duy trì. Người dùng không tự điền phần này.
### Name (Tên của Object)
- Khái niệm: Là chuỗi ký tự do bạn tự đặt (hoặc hệ thống tự sinh) để định danh cho một object, người dùng dùng tên này để gọi và tương tác hàng ngày (ví dụ: kubectl get pod my-app-web).
- Quy tắc đặt tên:
    + *Phải là một chuỗi chữ và số hợp lệ (RFC 1123 subdomain)*: chỉ chứa chữ thường, số, dấu gạch ngang (-), và dấu chấm (.)
    + *Giới hạn phạm vi (Scope)*: Mỗi object phải có một tên duy nhất trong cùng một Namespace. Tuy nhiên, hai object khác loại (hoặc cùng loại nhưng ở hai Namespace khác nhau) hoàn toàn có thể trùng tên nhau (ví dụ: Namespace dev có Pod web, Namespace prod cũng có Pod web — điều này hoàn toàn hợp lệ).
    + *Ứng dụng*: Dùng trong các câu lệnh kubectl hoặc khi các object gọi tên nhau trong file cấu hình (ví dụ: Service trỏ đến tên của Deployment).
### UID (Unique ID - Mã định danh toàn cục)
- Khái niệm: Là một chuỗi số định danh toàn cầu (chuẩn UUID) được Kubernetes tự động sinh ra ngay thời điểm object được tạo ra trong cụm. Bạn không thể tự đặt hay thay đổi UID.
- Quy tắc phạm vi:
    + Mang tính độc nhất trên toàn bộ hệ thống cluster (và trên cả lịch sử của cluster đó).
- Mục đích sử dụng:
    + Giải quyết bài toán trùng lặp ngữ nghĩa: Nếu bạn xóa một object mang tên web-server ở Namespace dev, sau đó tạo một object mới tinh cũng mang tên web-server ở chính Namespace đó, đối tượng cũ và mới sẽ có cùng một Name nhưng UID hoàn toàn khác nhau.
    + Giúp Kubernetes phân biệt rõ ràng các thực thể trong các kịch bản theo dõi lịch sử, rác thải dữ liệu (garbage collection) hoặc phân tách các tham chiếu nội bộ ngầm.
### So sánh Name và UID

| Tiêu chí | Name (Tên) | UID (Mã định danh) |
|:---:|:---:|:---:|
| Do ai đặt? | Do người dùng tự định đặt hoặc hệ thống sinh mẫu. | Do Kubernetes tự động tạo ra bằng thuật toán UUID. |
| Tính độc nhất | Duy nhất trong phạm vi một Namespace. | Duy nhất trên toàn bộ Cluster (Toàn cục). |
| Có thể đổi không? | Có thể xóa đi tạo lại với tên khác, nhưng không sửa trực tiếp tên khi object đang sống. | Tuyệt đối cố định, không bao giờ thay đổi trong suốt vòng đời của object. |
| Mục đích chính | Phục vụ con người dễ đọc, dễ nhớ và thao tác qua lệnh. | Phục vụ hệ thống định danh chính xác tuyệt đối các thực thể bên trong database (etcd). |

## Các cách quản lý Kubernetes Object (Object Management)
Kubernetes chia việc quản lý các object này thành 3 phương pháp chính tùy thuộc vào nhu cầu vận hành:
- **Imperative Commands (Lệnh mệnh lệnh trực tiếp)**:   
    + Gõ trực tiếp các câu lệnh kubectl trên terminal để tạo, xóa hoặc sửa đổi nhanh (ví dụ: kubectl run nginx --image=nginx).
    + Môi trường khuyên dùng: Thích hợp cho việc học tập, làm quen, test nhanh hoặc chạy các tác vụ một lần (one-off tasks) ngay lập tức trên cụm.
    + Ưu điểm: Nhanh, tiện lợi khi test hoặc làm việc khẩn cấp.
    + Nhược điểm (So với quản lý qua file):
        * Không lưu lại lịch sử cấu hình (không có source control).
        * Không tích hợp được vào các quy trình kiểm duyệt mã nguồn (như Git PR review).
        * Không cung cấp mẫu (template) để tái sử dụng cho việc tạo object mới.
- **Imperative Object Configuration (Cấu hình mệnh lệnh qua file)**:
    + Sử dụng file cấu hình (YAML) nhưng tương tác bằng các lệnh trực tiếp dạng hành động (ví dụ: kubectl create -f pod.yaml hoặc kubectl replace -f pod.yaml).
    + Môi trường khuyên dùng: Thao tác trực tiếp trên từng file riêng lẻ.
    + Ưu điểm: 
        * Cho phép lưu trữ mã nguồn cấu hình lên hệ thống quản lý mã nguồn (Git).
        * Hỗ trợ quá trình review thay đổi trước khi đưa lên hệ thống.
    + Nhược điểm:
        * Hoạt động tốt nhất trên từng file đơn lẻ, xử lý theo thư mục (directories) khá hạn chế.
        * Cạm bẫy với lệnh replace: Lệnh này sẽ xóa sạch cấu hình cũ trên cụm và đè toàn bộ bằng cấu hình mới trong file. Nếu có một hệ thống bên ngoài tự động cập nhật trường nào đó của object (ví dụ: Service loại LoadBalancer tự sinh ra trường externalIPs), trường đó sẽ bị mất khi bạn chạy replace
- **Declarative Object Configuration (Cấu hình khai báo toàn diện - Khuyên dùng cho Production)**:
    + Sử dụng lệnh kubectl apply -f <file-or-directory>.
    + Cách hoạt động: Bạn chỉ cần chỉnh sửa trực tiếp trên file YAML, sau đó chạy lệnh apply. K8s sẽ tự động thông minh nhận biết phần nào thay đổi để cập nhật mà không cần quan tâm trước đó trạng thái là gì. Đây là nền tảng của mô hình GitOps hiện đại.
    + Môi trường khuyên dùng: Môi trường Production quy mô lớn, là nền tảng cốt lõi của GitOps hiện đại.
    + Ưu điểm vượt trội:
        * Tự động nhận diện hành động: kubectl apply tự thông minh nhận biết object nào cần create, object nào cần patch (cập nhật) mà không cần bạn phải ra lệnh cụ thể.
        * Hỗ trợ xử lý theo thư mục: Quản lý nguyên cả một thư mục chứa hàng chục file cấu hình phức tạp cực kỳ mượt mà.
        * Bảo toàn thay đổi ngoại vi: Nếu một tiến trình khác (hoặc controller khác) có sửa đổi trực tiếp trên đối tượng đang chạy, những thay đổi đó vẫn được giữ lại chứ không bị đè mất một cách vô lý.
**Quy tắc vàng (Golden Rule)**: "Một Kubernetes Object chỉ nên được quản lý bằng `MỘT` phương pháp duy nhất."
Việc trộn lẫn các phương pháp (ví dụ: vừa dùng lệnh kubectl run tạo xong, lại vừa dùng file YAML kubectl apply để sửa đổi trên cùng một đối tượng) sẽ dẫn đến các hành vi không thể đoán trước (`undefined behavior`).

## Labels và Selectors
### Labels (Nhãn dán)
- Bản chất: Là các cặp khóa-giá trị (key: value) được gắn trực tiếp vào các object (như Pod, Deployment, Node...). Bạn hoàn toàn có thể tự do định nghĩa bất kỳ label nào mình muốn.
- Quy tắc đặt tên (Key & Value):
    + Key: Tối đa 63 ký tự, bao gồm chữ cái, số, dấu gạch ngang (-), gạch dưới (_), và dấu chấm (.), bắt buộc phải bắt đầu bằng chữ hoặc số. Có thể kèm theo tiền phong (prefix) dạng domain (ví dụ: app.kubernetes.io/name).
    + Value: Tương tự, tối đa 63 ký tự (có thể để trống).
- Mục đích sử dụng: Gắn các thuộc tính mô tả cho object.
    + Ví dụ: Bạn có 10 chiếc Pod, bạn gắn nhãn environment: production cho 5 Pod chạy thật và environment: development cho 5 Pod chạy thử nghiệm. Hoặc gắn nhãn tier: frontend, tier: backend.

### Selectors (Bộ chọn lọc)
- Bản chất: Là công cụ để "truy vấn" và tìm kiếm các object dựa trên các Labels mà chúng đang mang. Các object khác (như Service, Deployment, ReplicaSet) sử dụng Selector để gom nhóm và điều khiển các Pod phù hợp.
- Hai loại Selector chính trong Kubernetes:

**Equality-based requirement (Bộ chọn dựa trên phép so sánh bằng)**
- Cho phép lọc các object khớp chính xác hoặc khác biệt với giá trị của nhãn:
    + `=` hoặc `==`: Bằng (Ví dụ: environment = production)
    + `!=`: Khác (Ví dụ: environment != development)
**Set-based requirement (Bộ chọn dựa trên tập hợp - Linh hoạt hơn)**
- Cho phép lọc dựa trên sự tồn tại của khóa (key):
    + `in`: Thuộc một danh sách (Ví dụ: environment in (production, staging))
    + `notin`: Không thuộc danh sách (Ví dụ: environment notin (dev, test))
    + `key (hoặc exists)`: Tìm các object có chứa khóa đó (bất kể giá trị là gì).
    + `doesnotexist` (hoặc `!key`): Tìm các object không chứa khóa đó.
    + Ví dụ: environment in (production, qa) sẽ chọn tất cả Pod có nhãn environment là production hoặc qa.

## Namespace
### Bản chất của Namespace
- Namespace cung cấp cơ chế phân chia một cụm Kubernetes vật lý thành nhiều "cụm ảo" (virtual clusters) độc lập về mặt logic.
- Phạm vi áp dụng: Phù hợp cho môi trường có nhiều người dùng, nhiều nhóm dự án cùng chia sẻ một cluster (multi-tenant nội bộ). Nếu chỉ có vài người dùng hoặc môi trường thử nghiệm nhỏ, thường không nhất thiết phải chia nhiều namespace.
- Phân vùng tên gọi (Scope for Names): Tên của một đối tượng chỉ cần là duy nhất trong cùng một namespace. Hai namespace khác nhau có thể chứa hai Pod có cùng tên (ví dụ: namespace development và production đều có thể chứa Pod tên là api-server).
### Các Namespace mặc định khi khởi tạo Cluster
- Khi bạn dựng một cụm Kubernetes mới, hệ thống tự động sinh ra 4 namespace cốt lõi:
    + *default*: Namespace mặc định cho các đối tượng mà bạn không chỉ định namespace cụ thể.
    + *kube-system*: Chứa toàn bộ các đối tượng do chính Kubernetes tạo ra để vận hành cụm (Control Plane components, CoreDNS, kube-proxy, CNI plugins).
    + *kube-public*: Tự động được tạo và mở quyền đọc công khai cho tất cả người dùng (kể cả chưa xác thực - unauthenticated). Thường dùng để lưu trữ các thông tin công khai về cluster (như config map để bootstrap cụm).
    + *kube-node-lease*: Chứa các đối tượng Lease liên quan đến từng Node. Mỗi node gửi heartbeat định kỳ qua lease này để API Server biết node còn sống hay đã chết, giúp giảm tải đáng kể cho hệ thống so với cơ chế kiểm tra cũ.
### Namespace-scoped vs Cluster-scoped Objects
- Không phải mọi tài nguyên trong Kubernetes đều nằm trong Namespace:

| Loại phạm vi | Đặc điểm | Các tài nguyên tiêu biểu |
|---|---|---|
| Namespaced (Nằm trong Namespace) | Bắt buộc phải gắn với một namespace. Tên là duy nhất trong namespace đó. | Pod, Service, Deployment, ConfigMap, Secret, PersistentVolumeClaim (PVC) |
| Cluster-wide (Không nằm trong Namespace) | Tồn tại ở cấp độ toàn cụm, tên phải là duy nhất trên cả cluster. | Node, Namespace, PersistentVolume (PV), StorageClass, ClusterRole, ClusterRoleBinding |

- Bạn có thể kiểm tra trực tiếp bằng lệnh:
    + Xem tài nguyên thuộc namespace: kubectl api-resources --namespaced=true
    + Xem tài nguyên toàn cụm: kubectl api-resources --namespaced=false
### Định tuyến mạng và DNS giữa các Namespace
- Namespace không phải là bức tường lửa cách ly mạng mặc định. Mặc định, Pod ở namespace A vẫn có thể gọi trực tiếp sang Pod/Service ở namespace B qua mạng.
- Khi truy cập một Service qua DNS nội bộ của cụm:
    + Cùng Namespace: Gọi tắt bằng tên Service:
    <service-name> (ví dụ: database)
    + Khác Namespace: Phải dùng tên miền đầy đủ (FQDN - Fully Qualified Domain Name):
    <service-name>.<namespace-name>.svc.cluster.local
    (Ví dụ: Service database ở namespace backend sẽ được gọi bằng database.backend.svc.cluster.local)
**Lưu ý:**Nếu muốn ngăn chặn hoàn toàn việc các namespace nói chuyện với nhau, bạn phải cấu hình NetworkPolicy.
### Tự động gắn nhãn (Automatic Labeling)
- Kể từ Kubernetes 1.21, cơ chế Kubernetes API Server tự động gán nhãn bất biến lên tất cả các namespace:
```bash
kubernetes.io/metadata.name: <tên-namespace>
```
- Nhãn này cực kỳ hữu ích khi bạn viết các quy tắc NetworkPolicy hoặc PodAffinity cần chọn đích danh một namespace nào đó bằng namespaceSelector mà không cần phải tự tay đi đánh nhãn thủ công cho namespace đó.
### Giới hạn tài nguyên (Resource Quotas & Limits)
- Namespace là đơn vị cơ bản để chia sẻ và kiểm soát tài nguyên phần cứng:
    + *ResourceQuota*: Giới hạn tổng dung lượng CPU, RAM hoặc số lượng đối tượng tối đa mà một namespace được phép tiêu thụ (ví dụ: Team Dev chỉ được dùng tối đa 16 Core CPU và 32GB RAM).
    + *LimitRange*: Thiết lập giới hạn cấu hình mặc định (min/max/default request & limit) cho từng Pod/Container đơn lẻ khi tạo bên trong namespace đó.
### Lệnh hay dùng
```bash
# List namespace
kubectl get ns
# Create namespace
kubectl create ns dev
# Delete namespace
kubectl delete ns dev
# Describe namespace
kubectl describe ns dev
# Get Pod trong namespace
kubectl get pods -n dev
# Get tất cả resource trong namespace
kubectl get all -n dev
# Get resource ở tất cả namespace
kubectl get pods -A
# Tạo resource trong namespace
kubectl create deployment nginx --image=nginx -n dev
# Đổi namespace mặc định
kubectl config set-context --current --namespace=dev
# Kiểm tra namespace mặc định hiện tại
kubectl config get-contexts
```
